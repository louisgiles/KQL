2. MAKE RESEARCH WRITES, READ-BACK AND STATUS CONSISTENT
Affected: section 3.8; persistence and failure tests; Sources & updates status.

Finding:
upsertResearch writes articles individually. If a later write fails, earlier
writes may already be committed. The proposed fatal handler then reports
updated: 0 and rejected: 0, which can misrepresent what actually happened.
Counting rows with kind = research also does not prove the submitted payload
was saved: an older research row could already satisfy that check. Duplicate
canonical URLs in one submission can make count-based verification fail.

Required revision:
- Define one concrete policy. Prefer committing the accepted article updates
  as one atomic batch if the selected D1/Drizzle interface supports it. Verify
  that interface before prescribing its implementation. Otherwise explicitly
  retain partial writes and report their actual committed count.
- Reject or deduplicate repeated canonical article URLs before writes, using
  a documented deterministic rule.
- Read back the expected IDs and persisted article fields, including source
  URLs and tailored packs, and compare them with the submitted normalized
  payloads. A row count alone is insufficient.
- Distinguish a failed write from a failed verification after a successful
  commit. Do not claim zero saved changes when commits may have succeeded.
- Keep rejected counts accurate. Define when lastResearch advances under the
  chosen policy; it should represent a successfully saved and verified update.
- If D1 itself is unavailable, storing researchStatus can also fail. Make that
  a logged failure with best-effort status persistence, rather than promising
  that status can always be written.

Acceptance:
Add a test that injects a failure after an earlier article write, or within the
atomic batch. Assert the chosen rollback/partial-write behaviour and accurate
status. Add duplicate-URL and read-back-mismatch cases. Existing article IDs,
Actioned marks, hunts and notes remain unchanged by enrichment.

3. STRENGTHEN WHAT QUALIFIES AS SOURCE-REVIEWED RESEARCH
Affected: section 3.8 prompt, tool-result handling and entry acceptance.

Finding:
Membership in the retrieved-URL set helps prevent invented citations, but it
does not establish that the cited page supports a particular claim. The set
currently combines search results and successfully fetched pages. The prompt
also asks for verified table schemas without an acceptance requirement that
the relevant documentation was actually retrieved.

Required revision:
- Track successful full-page fetches separately from search-discovered URLs.
  Require a successful fetch of the primary report used for each researched
  briefing. If it is inaccessible, report the evidence gap and retain the
  original feed entry rather than promote it to a source-reviewed briefing.
- Require successful retrieval of the relevant Microsoft Learn table
  documentation before accepting a tailored hunt pack. Check that its declared
  tables have the corresponding documentation evidence. If that evidence is
  missing, omit the tailored pack and explain the gap; a supported briefing
  can still be saved without a query.
- Require the research process to tie each factual claim to supporting source
  text and to qualify uncertainty. Be explicit that URL checks and retrieval
  checks validate provenance, not the truth or entailment of every claim.
- Preserve the existing separation between observed activity and proposed
  hunts. Never turn documentation retrieval into a claim of tenant validation.

Acceptance:
Add cases for a search-discovered primary URL whose fetch failed, and a
tailored pack without successfully retrieved schema documentation. Neither
case may silently acquire stronger evidence or validation labels than the
available material supports.

4. ENFORCE THE RESEARCH BUDGET ACROSS CONTINUATION REQUESTS
Affected: section 3.8 request loop; section 4.1 cost notes; research tests.

Finding:
Anthropic documents max_uses for web search and web fetch as per-request
limits. Reusing max_uses: 10 on as many as five requests does not establish
the proposal's claimed ten-search limit for the entire daily run.

Required revision:
- Keep one run-wide search budget and one run-wide fetch budget. Account for
  tool use across continuation responses and pass only the remaining allowance
  to each subsequent request. Specify the documented behaviour when an
  allowance is exhausted; do not reset it on pause_turn.
- Retain the overall deadline and request-count cap. Specify the outcome when
  the budget or deadline ends before a valid submission.
- Correct the cost note to distinguish tool-call limits from token costs.
  max_tokens is also a per-response ceiling, not a daily spending cap.
- Keep this to a small amount of explicit state in the existing research
  function, with no new scheduling or orchestration layer.

Acceptance:
A mocked first response consumes part of the budget and pauses. The next
request receives the remaining allowance. Exhaustion cannot reopen a fresh
budget, and the final status accurately describes any incomplete research.

5. DEFINE ZERO-RESULT AND PARTIAL-RESULT OUTCOMES
Affected: ResearchStatus semantics; section 3.8; section 3.9 status copy; tests.

Finding:
The target is 3–6 defensible briefings, but the acceptance loop can retain zero
or fewer than three. The plan does not fully specify how those outcomes are
reported. A structurally valid submission alone must not count as a successful
research refresh when every entry is rejected.

Required revision:
- Zero accepted entries: ok: false, updated: 0, truthful rejected count and a
  useful reason. Preserve earlier intelligence and lastResearch.
- One or two accepted entries: retain the valid saved results, identify the
  outcome as partial in the UI, and explain a known shortfall where possible.
  Do not manufacture additional threats to hit a quota.
- Three or more accepted entries with some rejections: report both counts so
  the user can see the research coverage and rejected submissions.
- Specify these cases in the existing status contract and UI logic. Prefer
  deriving partial status from the existing counts where sufficient; avoid
  introducing a separate run-history subsystem.

Acceptance:
Tests cover an empty submission, all entries rejected, two valid entries, and
a mixed valid/rejected submission. The UI accurately distinguishes a failed
attempt, a partial refresh and a completed refresh with rejected entries.
