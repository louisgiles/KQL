### The result we owe

By 08:00 the register holds a short list of **finished hunt packs** an analyst can run the same day, in the order they should be run. Each one is likely to find something now, exact enough that a match is almost certainly the real thing, and clear about what a match means. Six finished packs beat fourteen thin ones.

The register keeps two lists, and never mixes them:

- **Low-severity packs (H IDs).** Unwanted software. This is the main list.
- **Escalation packs (E IDs).** Software that arrives by the same routes as the confirmed hits but that public reporting classes as malware. Run 03 was right to keep these out of the low-severity list. They still belong in the register, in their own section headed "Same route, not low severity", because they are the likeliest finds of all on estates that have already had PDF Spark. A match there is an incident lead, never a routine finding.

### What "finished" means

A pack is finished only when all of this is true. Otherwise its index status is `Incomplete: <what is missing>`.

1. **Likely now.** At least one dated source from the last 12 months shows it being distributed or found on machines: a vendor detection release, an incident write-up, a prevalence figure, or a download page that is live today (give the date you checked). The index shows the newest evidence date.
2. **Exact identifiers.** One identifier table per pack, one row per identifier: product; type (signer, version information, process name, folder, scheduled task, service, registry key, hostname, detection name); the exact value as the source shows it; the Log Analytics table and column it is matched against; `standalone` or `pair with <identifier>`; source.
3. **Works without command lines.** Every product has at least one `standalone` identifier that does not depend on command-line data.
4. **No generic names standing alone.** `native.exe`, `Update.exe`, `Updater.exe`, `uninstall.exe`, `Setup.exe`, `net_updater32.exe` and the like are always `pair with` a folder, signer or version-information value.
5. **What a match means.** One sentence on what a match proves, one on the artefacts that turn it into an incident, one on who might have it legitimately.

## Standing guidance

Applies to every run until a later review changes it.

1. **Stay in one file.** Change only `threat-work/hunts/high-probability-low-severity.md`. No other repository path.
2. **Add, don't rebuild.** Never delete, renumber or reword existing cards, IDs or footnotes unless a review or new evidence calls for that specific change. Record each such change in the run log.
3. **Check your own edit before committing.** Every `[^id]` reference has a definition and every definition is referenced. Every index link resolves. The header's run number and active-candidate count match the index and the run log.
4. **Likelihood needs evidence, and recent evidence counts most.** A candidate earns "high probability" from dated evidence that it is on machines now: live distribution, a recent vendor prevalence figure, or a dated sighting in an organisation. Evidence from the last 12 months outranks anything older. An identifiable artefact alone is not likelihood.
5. **A shortfall is a valid result.** One well-evidenced candidate beats two thin ones. If nothing clears the bar, add none and spend the run strengthening the evidence on existing cards.
6. **Quote what a pivot rests on.** For any path, argument or service name taken from a sandbox report, record the exact string as shown and where in the report it appears. Two detonations of one file hash are one sample.
7. **Build packs around what has already hit.** Siblings of a confirmed hit are the strongest leads: other products from the same publisher, installer framework or advertising route. Where several share those, write one pack with a per-product identifier table, each identifier sourced. A pack counts as one candidate. A product the owner already knows is calibration and goes in the already-covered table, not into a pack as new.
8. **Check the signer before calling anything low severity.** The signer table from Unit 42's May 2026 research is copied into the sweep sheet under "Escalate on match". A product whose signer is in it goes in the escalation list, whatever another source calls it. Record the disagreement in the pack.
9. **After the last review.** Review 008 on 13 November 2026 is the last review. Its *Next run* list holds for every later run. A new pack needs a source from the last 12 months that shows the software on machines. A live download page is not enough by itself.

## Verified sweep sheet

Identifiers a reviewer has read in the cited source. This is the list to hunt from. Reviewers add to it at every review. The research run does not edit it.

- `standalone` means the value is specific enough to match by itself. `pair` means match it only together with another identifier for the same product.
- Severity in the first table is `low` (unwanted software), `contested` (sources disagree, so look closer on a match) or `calibration` (a confirmed previous hit).
- Hostnames are defanged. A lookup of a hostname is a lead, never proof of an install.
- Signer strings vary in case and punctuation between sources. Match them without case sensitivity.
- Source keys are listed at the end of the sheet.

**Where each type is matched in Log Analytics.** The table has to be ingested in the workspace.

| Type | Table and column |
| --- | --- |
| Signer | `DeviceFileCertificateInfo.Signer`, joined on `SHA1` to `DeviceProcessEvents` or `DeviceFileEvents` |
| Version information | `DeviceProcessEvents.ProcessVersionInfoCompanyName`, `ProcessVersionInfoProductName` and `ProcessVersionInfoFileDescription` |
| Process name, folder, command line | `DeviceProcessEvents.FileName`, `FolderPath`, `ProcessCommandLine` |
| File | `DeviceFileEvents.FileName` and `FolderPath` |
| Scheduled task | `DeviceEvents` where `ActionType` is `ScheduledTaskCreated`, name in `AdditionalFields` |
| Service | `DeviceEvents` where `ActionType` is `ServiceInstalled`, name in `AdditionalFields` |
| WMI consumer | `DeviceEvents` where `ActionType` is `WmiBindEventFilterToConsumer`, name in `AdditionalFields` |
| Registry key | `DeviceRegistryEvents.RegistryKey` |
| Hostname | `DeviceNetworkEvents.RemoteUrl` |
